sherpa-onnx 2.0.0 升级决策报告

react-native-nitro-onnx（vendored 基线：1.13.7） · 2026-10-28 · 结论与证据均基于上游源码/release 实况核对

总结论

建议跟进 2.0.0。 C API 层零符号删除、零函数签名破坏，全部破坏性变化要么是「结构体尾部追加字段」（对仓库现有的零初始化代码天然兼容），要么是「本仓库根本不读的字段类型扩展」（SpeechSegment.start、CircularBuffer）。仓库当前代码无需改动即可通过编译；真正要动的是三件事：① TTS 的 espeakNgData（data_dir）在 2.0.0 被忽略，需迁移到已存在的 lexicon 通道并为英文语音补词典；② vendoring 替换（Android 官方 tar 直换、iOS 沿用既有自建流程）；③ 全引擎回归。作为回报拿到 VAD 长流 SIGSEGV 修复（#4079）与 ZipVoice 短文本堆溢出修复（#4051），两者都直接命中本库使用场景。

2. espeak-ng 移除的真实影响（最关键）

2.1 事实

  • 2.0.0 移除 espeak-ng 与 piper-phonemize（PR #4055，母 Issue #3731）。没有换成新的内置 G2P 库，改为两条前端：① 内置 lexicon 词典前端（lexicon.txt 查词，无 GPL 依赖，OOV 词跳过）；② 外部自行音素化后经新增的 GenerationConfig.phoneme_codepoints / .tokens 传入。
  • 五个 TTS config 的 data_dir 全部标注 @deprecated Ignored since v2.0.0 —— 字段保留（ABI 不变）但不再被读取。
  • 官方明确模型权重文件（.onnx / tokens.txt）无需修改、无需重下（"no alterations required to model files themselves"）。

2.2 对本库的实际影响（已对照代码）

  • 仓库 espeakNgData 字段（TS OnnxSpeech.nitro.ts:263 → Tts.cpp:47 → TtsEngine.cpp:72）写的就是 C 侧 data_dir（kokoro:102 / vits:112 / matcha:121 / zipvoice:149）。升级后该字段变 no-op（无害但无效）。
  • 仓库已存在完整 lexicon 通道：TS lexicon → TtsEngine.cpp:70 → c.model.{kokoro,vits,matcha,zipvoice}.lexicon（:104/:110/:119/:150）；Kokoro 分支已强制 checkFile(lexicon)（:98）。README 中 Kokoro 已要求 lexicon.txt、VITS 标记 lexicon 可选。
  • 因此迁移动作很小：espeakNgData 标 deprecated + 英文语音补齐 lexicon.txt。中文词典型语音（melo/vctk/aishell3）与 Kokoro 中英（自带 lexicon-us-en.txt / lexicon-zh.txt）不受影响；纯 Piper 英文旧包（glados/libritts/lessac，目录里只有 espeak-ng-data、无 lexicon.txt）不补词典则全部 OOV 不出音 —— 这是升级前需要盘点的资产项。
  • 词典来源：官方 lexicon-en-us.txt（tts-models release）或社区免 GPL 词典 voicegarden-lexicons。Pocket 不依赖 espeak-ng（不写 data_dir），完全不受影响。

4. 价值 vs 成本

4.1 对本库有实际价值的修复（2.0.0 相对 1.13.7）

  • #4079 VAD 长流 SIGSEGV（采样位置 int32→int64）—— 本库做 streaming VAD，长时间录音分段是核心场景，此修复免费获得且升级即生效。
  • #4051 ZipVoice 短文本 speed>1 堆溢出 —— 本库支持 ZipVoice（TtsEngine 有 speed 参数路径），直接修掉一个内存安全 bug。
  • #4044 Create* 异常捕获返回 NULL —— 仓库已全量 NULL 检查，异常不再崩溃、可向上抛 JS 异常，稳定性增强。
  • #4062/#4064 TTS 非 BMP（emoji 等）文本处理修复 —— 需回归测试中文/emoji 混合文本。
  • #3950 GetEmbedding 新增 —— 纯增量，未来可向 TS 暴露 speaker embedding 导出能力。

4.2 升级成本清单（破坏性工作量预估）

项目工作量说明
vendoring 替换（Android 4 ABI + include 头 + 本地 lib/*.a）低官方 tar 直换，结构同构；iOS 沿用自建流程重新出 xcframework
TTS 迁移：espeakNgData 标 deprecated、英文语音补 lexicon.txt低-中代码改动 ≈ 文档/类型注释 + 资产盘点；如做「lexicon 缺省自动回退官方 lexicon-en-us.txt」需小改 TtsEngine.cpp:70-150
cpp 代码编译改动≈ 00 删除、0 签名破坏、结构体尾部追加兼容零初始化；无需改任何 cpp 文件即可过编译
回归测试中全引擎过一遍：TTS（5 模型 + 中文/emoji）、VAD 长流、diarization（confidence 新字段可选）、ASR/KWS/LID/denoiser/embedding

5. 结论与建议

  • 是否跟进：跟进 2.0.0。 C API 破坏面几乎为零且全部兼容现有代码；两个直接命中本库场景的 bug 修复（VAD 长流 SIGSEGV、ZipVoice 堆溢出）是实打实的收益；espeak-ng 移除的实际改动量因仓库已有 lexicon 通道而很小。
  • 若跟进，改什么（清单）：
    1. 替换 thirdparty/sherpa-onnx/：android 4 ABI × 4 .so + libonnxruntime.so、include/sherpa-onnx/c-api/c-api.h、本地 lib/*.a；iOS 用既有构建脚本重出 SherpaOnnxC.xcframework。
    2. TTS 语义迁移：espeakNgData 标注 deprecated（保留字段防破坏现有 TS API）；TtsEngine.cpp 的 data_dir 赋值改为仅当未提供 lexicon 时尝试 lexicon-en-us.txt 兜底或直接移除；README/类型注释更新；盘点打包的 TTS 语音，英文 Piper 系补 lexicon.txt。
    3. 可选增强：暴露 GenerationConfig.phoneme_codepoints 支持外部音素化；暴露 GetEmbedding。
    4. 回归：全引擎 + TTS 中文/emoji 文本 + VAD 长时间流。
  • 若不跟进的风险：① VAD 长流 SIGSEGV 与 ZipVoice 堆溢出持续存在（都是运行时崩溃/内存安全级别）；② 上游 2.0.x 后续版本基于 2.0 API 演进，拖延使累积 diff 变大；③ 1.13.x 是最后带 espeak-ng 的版本线，但已 vendored，不影响继续使用；④ 无风险积累之外的其它硬性理由。总体「不跟」的代价 > 「跟」的成本。
